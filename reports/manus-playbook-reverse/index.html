前端架構 模板機制 Agent 引擎 商業漏斗 情報來源 8+

研究方法：仿照先前 arthurk01 股票報告的逆向工程做法，分四層由外而內拆解：(1) Playbook 頁面的前端與內容架構、(2) 單一 playbook 的模板解剖、(3) 背後 Manus Agent 引擎（用官方部落格＋洩漏的 system prompt 交叉驗證）、(4) 整套的商業獲客設計。最後給如菓可移植的打法。

關鍵發現先講：Manus 的核心機密幾乎是「半公開」的——system prompt 在 2025 年被用戶輕鬆問出（直接要求印出 /opt/.manus/ 目錄即可），官方共同創辦人甚至主動寫部落格公開設計原則。所以這份逆向工程不靠猜，靠的是把官方說法與洩漏實證對照。

第一層：Playbook 頁面的前端與內容架構

每個 playbook（如 video-generator）都是同一個頁面模板填不同內容，固定六段式結構：

區塊作用逆向觀察
① Hero 標題區工具名＋一句價值主張＋CTA 按鈕標題即 SEO 關鍵字（「AI 視頻生成器」）
② 使用案例卡片2-3 個應用場景示意降低「我能用它做什麼」的想像門檻
③ 工作流程圖固定 3-4 步：描述→AI 處理→輸出把 agent 的複雜過程簡化成「三步就好」
④ FAQ（約 10 題）免費嗎/難不難/商用授權/生成時間大量長尾關鍵字，吃 Google 搜尋流量
⑤ 品牌標語"Less structure, more intelligence."每頁重複，強化品牌記憶
⑥ 頁腳 + CTA多欄導航＋「開始生成」所有 CTA 指向同一個 Manus App 入口

技術線索：Next.js/React 單頁、15 語系、無明顯 Schema.org 標記、© 2026 Meta（Manus 已被 Meta 整併）。

這套「一個模板 × N 個落地頁」就是教科書級的 Programmatic SEO：80 個 playbook = 80 個吃不同關鍵字的入口頁，全部導向同一個產品。如菓的對應版本：把「台中系統櫃」「老屋翻新」「交屋裝潢」等每個關鍵字各做一頁落地頁（同模板換內容），全部導向估價預約——這正是瑪莉行銷漏斗可以用 Open Design 量產的東西。

第二層：單一 Playbook 的模板解剖

逆向結論：一個 playbook = 一份「預填好的結構化提示詞 + 固定輸出格式」。它不是新功能，是把同一個 Agent 引擎用「包裝好的任務說明」叫起來。拆開來看三個零件：

  1. 角色與目標預設——例如市場研究工具，已內建「你是市場分析師，產出含數據分析＋策略見解的報告」
  2. 輸入欄位設計——把使用者要給的資訊拆成幾個明確欄位（主題／地區／時間），降低「不會下提示詞」的門檻
  3. 輸出格式鎖定——固定章節結構（數據→消費者→競爭→商機），所以每次產出長得一樣專業

證據：不同 playbook 共用同一批底層工具，只是「任務說明」不同——這跟我們的賈維斯助手團隊（同一個我，換不同人格設定檔）是完全相同的設計思路。

這正是我們已經在做的事，而且我們做得更深：泰咪的報價資料庫、艾莉兒的工法五段式、風格轉換 SOP、講稿模板——每一個都是如菓版的 playbook。Manus 驗證了這條路是對的。可以再系統化：把高頻任務（建案追蹤、提案書、報價審核）都寫成固定「輸入欄位＋輸出格式」的模板，老闆只要填欄位。

第三層：背後的 Agent 引擎（核心機密）

這層是真正值錢的部分。資料來源：Manus 共同創辦人 Yichao Ji 的官方部落格〈Context Engineering〉＋ 2025 年洩漏的 system prompt 與工具清單，兩者互相印證。

3-1　運作循環（Agent Loop）

分析事件流 → 選 1 個工具 → 等執行結果 → 回填 context → 再選下一個工具 → ⋯ → 完成 → 待命

關鍵設計：一次只呼叫一個工具，耐心重複。平均一個任務跑約 50 步工具呼叫。洩漏的工具集有 30+ 個，分六類：

類別工具（節錄）
通訊message_notify_user（單向報進度）、message_ask_user（必要才問）
檔案file_read / file_write / file_str_replace / file_find
Shellshell_exec / shell_view / shell_kill_process
瀏覽器browser_navigate / click / scroll / console_exec
搜尋info_search_web
部署deploy_expose_port / deploy_apply_deployment

沙箱：每個 session 一個獨立 Ubuntu 22.04 容器，含 Python 3.10 / Node 20 / sudo / 連網，閒置自動休眠。

3-2　官方親口的六大 Context Engineering 原則

原則做法為什麼（解決什麼）
① KV-Cache 至上提示前綴固定、不放時間戳、只追加不改寫輸入是輸出的 100 倍；命中快取成本差 10 倍（$0.3 vs $3/MTok）
② 工具用遮罩不用刪用狀態機 + logits 遮罩開關工具動態增刪工具會讓 KV-cache 失效、模型混亂
③ 檔案系統當記憶把資料寫檔，context 只留路徑/URL避免 context 爆炸，又能隨時回讀
④ todo.md 重述目標不斷重寫待辦清單到 context 尾端50 步長任務防「迷失在中間」、防跑題
⑤ 保留失敗痕跡錯誤、堆疊追蹤不擦掉讓模型看到失敗、隱性學習、少犯同錯
⑥ 避免少樣本陷阱刻意加變化、不堆太多相似範例防模型陷入機械式模仿
這六條對我（賈維斯）的運作直接有用：
• ④ todo.md 重述——長任務（像剛剛的 BNI 簡報多版迭代）我可以用待辦清單頂住目標不跑偏
• ③ 檔案當記憶——這正是我們 data/ 知識庫＋ LLM Wiki 在做的；Manus 證明這是對的架構
• ⑤ 保留失敗——呼應老闆昨天要的格局偏移分析報告：錯誤留檔、寫成 SOP，比擦掉重來更值錢
• ① 成本意識——能省 context 輪數就省（這也是老闆 CLAUDE.md 的 TOKEN DISCIPLINE 鐵則）

3-3　System Prompt 透露的行為鐵則

  • 資訊優先序：官方資料 API > 網路搜尋 > 內部知識（跟我們「事實查核、禁止幻想」同精神）
  • 必須用工具、禁止純文字打發：每一步都要實際動作
  • 所有 URL 必須用瀏覽器驗證過才引用（呼應我們「VERIFY BEFORE DONE」）
  • 主動報進度、但少打擾：notify 常用、ask 只在必要——跟老闆要的「長任務要回報」一模一樣

第四層：商業獲客設計（它靠這個賺什麼）

整套 playbook 的商業邏輯：

  1. SEO 流量入口：80 個 playbook 落地頁 + 每頁 10 題 FAQ = 數百個長尾關鍵字，免費吃 Google 搜尋流量
  2. 降門檻轉化：把「會用 AI」變成「按按鈕」，讓不會下提示詞的人也能成功 → 立刻體驗到價值
  3. 點數變現：免費試 → 上癮 → 任務要點數 → 付費訂閱（典型 PLG，product-led growth）
  4. 內容飛輪：26 篇部落格 + Academy 課程 + 社群，持續產內容餵 SEO 與信任

本質：用「免費好用的工具頁」當魚餌，把搜尋流量變成付費用戶。工具本身就是行銷素材。

如菓的可移植版本：「免費工具頁獲客」是設計公司很少做但很有效的招。例如做一個「免費系統櫃估價試算」「免費老屋翻新風格測驗」的網頁工具，吃「台中系統櫃估價」這類搜尋字 → 用戶試用留資料 → 轉成丈量預約。工具本身就是內容行銷，比硬打廣告便宜。這個可以排進瑪莉的中長期計畫。

網路既有研究：別人已經拆過什麼

來源研究成果

官方部落格（Yichao Ji）六大 context engineering 原則，創辦人親述

洩漏事件的啟示：Manus 官方態度是「我們的工具設計不是秘密、類似學界常見做法」——也就是說，護城河不在 prompt，在於工程整合度（KV-cache 優化、沙箱、50 步穩定執行）與品牌/流量。這對我們的啟發：別迷信「神級 prompt」，真正的競爭力在累積的資料庫、可控的工作流、和在地專業。

總結：三句話帶走

  1. 一個 playbook = 預填提示詞 + 鎖定輸出格式，叫的是同一個 Agent 引擎——我們的助手團隊與資料庫就是同思路，且更貼合在地。
  2. 真正的技術在 context engineering 六原則（KV-cache、todo.md、檔案當記憶、保留失敗）——其中四條我可以直接拿來優化日常運作。
  3. 商業上它是 Programmatic SEO + PLG：免費工具頁當魚餌換付費。如菓可借這招做「免費估價/風格測驗工具頁」獲客。
